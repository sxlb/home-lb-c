总体结论

架构骨架健康，但存在一处会导致全站配置被静默重置的数据丢失级缺陷，以及随笔功能下线后遗留的一整套僵尸代码。

最紧急：音乐设置面板会重置全站配置

MusicPanel 保存时只提交 4 个字段，而 profileSchema 的所有字段都带 .default()，导致缺失字段被填默认值后整行写库。用户点一次「保存音乐设置」，昵称、头像、主题、壁纸、欢迎语、玻璃拟态等全部配置会被打回默认值。这是本次审计中唯一的数据破坏性缺陷，建议立即修复。

严重度分布

  • P0 严重（5 项）：音乐设置保存导致配置重置、音乐面板读不到已保存配置、音乐面板保存态失效；备份只覆盖 4 张表导致恢复丢数据、重置默认可把管理员密码降级为 123456（后两项见第 10 节）。
  • P1 逻辑/一致性（16 项）：幽灵字段 logoFont、孤儿字段 siteLinksIcon、showStats 语义与行为不符、sitemap 输出死链；链接 id 每次保存都变导致点击统计永久分裂、改密无法踢出其它设备、更新失败留下混合状态、统计数据无爬虫过滤（见第 09–11 节）。
  • 冗余可下线（18 项）：随笔功能全套残留（12 处）、公告单条接口、死导出与死枚举、无文档的一次性部署脚本。
  • 缺失能力（18 项）：季节特效无开关、首页模块无显隐控制、2FA 无恢复码、无登录审计；备份不覆盖作品集/技能云/公告、无会话管理、无拖拽排序、无批量操作、无告警通知。

报告分两轮产出：第一轮（第 01–08 节）覆盖面板功能、API 路由、开关链路；第二轮（第 09–13 节）深入认证、数据一致性、更新通道、统计采集与交互无障碍层。

02

P0 · 严重缺陷

这三项集中在音乐设置面板，共同构成「配置被重置 + 读不到值 + 无反馈」的完整故障链。

P0-1 数据丢失保存音乐设置会重置全站配置

MusicPanel 的保存请求体仅含 4 个键，但 profileSchema 中每一个字段都写了 .optional().default()，safeParse 会把缺失字段补成默认值；而 /api/profile 的 PUT 会把 parsed.data 的全部字段写入数据库。两者叠加的结果是：未提交的字段被默认值覆盖。

# 触发链路 components/admin/MusicPanel.tsx:28 body: JSON.stringify({ songApi, songServer, songId, musicPlayerMode }) lib/validation.ts:50-442 每个字段均 .optional().default(...) → 缺键被填默认值 app/api/profile/route.ts:41-103 解构全部字段（含 nickname / avatar / theme / accentColor / welcomeMessages …） app/api/profile/route.ts:179-181 prisma.profile.update({ where, data }) ← data 含全部默认值 # 后果 点一次「保存音乐设置」→ nickname 变回「无名」、avatar 清空、theme 回 system、 accentColor 清空、glassOpacity 回 28、welcomeMessages 回内置 5 句 … # 正确写法参照（部分更新） app/api/weather-setting/route.ts:29-36 data: { weatherProvider, amapKey, ... } ← 只写自己负责的 6 个字段 ✓

修复方向：改用 useProfileForm({ id: "music", label: "音乐设置" })。该 Hook 会 loadProfile(true) 取最新基线，仅合并本面板改动过的字段后提交，与 ThemePanel 保持一致。

P0-2 读取失效音乐面板读不到已保存的配置

组件通过 props 接收 profile，但渲染处没有传参，于是 profile?.songApi 恒为 undefined，所有输入框初始值都是空 / netease / card。用户看到的是"空表单"，一旦保存就会把真实配置写成空值（与 P0-1 叠加）。

components/admin/MusicPanel.tsx:12-20 interface MusicPanelProps { profile?: Record<string, unknown> } useState(profile?.songApi as string || "") app/admin/page.tsx:526 <MusicPanel /> ← 未传 profile
P0-3 状态失效保存按钮永远不显示"保存中"

saving 被硬编码为 false，因此 disabled 恒为假、文案恒为"保存音乐设置"。用户在网络请求往返期间可以反复点击，产生并发写入。同时该面板未注册全局保存，右下角"保存全部修改"不会覆盖音乐设置。

components/admin/MusicPanel.tsx:21 const saving = false; ← 常量，永不可变 components/admin/MusicPanel.tsx:104 <Button disabled={saving}>{saving ? "保存中..." : "保存音乐设置"}</Button> 缺失 useRegisterSave({ id: "music", ... }) ← 全文件无此调用
03

P1 · 逻辑与一致性问题

不直接破坏数据，但会导致开关"看起来有效、实际无效"，或让用户对开关语义产生误解。

P1-1幽灵字段 logoFont —— 存了值，前台完全忽略

校验层允许 19 种艺术字体，但前台映射表只剩 1 项，其余 18 个值（含默认值 zcool-kuail）全部落到同一个兜底字体。同时后台已无任何选择控件。结果是：这个字段对渲染零影响，且三处默认值互不相同。

lib/validation.ts:230-256 logoFont 枚举 19 种字体 app/hooks.ts:13-15 LOGO_FONT_CLASS = { "nowar-rounded": "font-art-nowar" } ← 仅 1 项 app/hooks.ts:253-255 LOGO_FONT_CLASS[logoFont || "nowar-rounded"] || "font-art-nowar" components/admin/ProfilePanel.tsx:43,107 仅类型声明与默认值，无表单控件 默认值漂移 prisma/schema.prisma:43 @default("zcool-kuail") components/admin/profileShared.ts:98 "zcool-kuail" app/hooks.ts:254 兜底 "nowar-rounded"

建议：二选一 —— 补齐后台字体选择器并恢复多字体映射；或连同 schema 字段、校验枚举一并下线，只保留 logoArtFont 开关。

P1-2孤儿字段 siteLinksIcon —— 能改、能存，前台不渲染

后台提供了"标题图标"输入框，getHomeData 也把它传了出来，但前台渲染 LinkTabs 时没有传这个 prop，组件侧也没有对应字段。管理员改了不生效。

components/admin/ProfilePanel.tsx:864-868 「标题图标」输入框 app/hooks.ts:250 siteLinksIcon: profile?.siteLinksIcon || "link" app/page.tsx:231-237 <LinkTabs siteLinks friendLinks projects siteTitle friendTitle /> ← 无 siteLinksIcon components/LinkTabs.tsx:50-60 props 仅 siteTitle / friendTitle
P1-3开关语义与行为不符：showStats 关掉了展示，却照旧采集

开关文案是「站点访问统计」，描述为"页脚显示浏览与访客数"。但代码里 showStats 只控制页脚是否展示，数据上报（POST /api/stats）是无条件执行的。用户以为关掉即停止统计，实际上 PV/UV 仍在记录 —— 这既是认知偏差，也是隐私声明层面的隐患。

app/page.tsx:246 <FooterLazy ... showStats={d.showStats} /> components/Footer.tsx:102 if (showStats && (todayPv > 0 || pv > 0 || uv > 0)) ← 仅控制展示 components/Footer.tsx:184-203 useEffect(() => { fetch("/api/stats", { method: "POST" }) ... }, []) ← 无 showStats 判断，始终上报

建议：把开关重命名为「页脚显示访问量」；若确需停止采集，应在 POST 前加 if (!showStats) return;。

随笔的前台路由和后台面板已删除，但 app/sitemap.ts 依然查询 prisma.article 并向搜索引擎提交 /articles 及详情页 URL。这些地址现在全部 404，会污染站点索引质量。

「保存全部修改」依赖各面板主动注册。两个配置类面板漏注册，导致用户在音乐 / 天气面板改完、再点"保存全部修改"，以为已全部落库，实际这两处改动被遗漏。

内核机制 · 认证与鉴权

这一层整体质量最高：时序攻击防护、双维度限流、内存上限保护、密钥启动校验都已到位。缺口集中在「会话生命周期」。

设计良好已具备的防护
  • 时序攻击防护：用户不存在时仍执行一次 bcrypt.compare（lib/auth.ts:187,228），避免通过响应时间探测账号是否存在。
  • 双维度限流：IP 维度与账号维度各自独立锁定（lib/auth.ts:213-246），既防单点爆破，也防多 IP 分布式爆破绕过。
  • 内存 DoS 保护：伪造 x-forwarded-for 撑爆 Map 时，先清过期条目、再按插入序淘汰（lib/auth.ts:71-82）。
  • 密钥启动校验：NEXTAUTH_SECRET 缺失 / 过短 / 仍为示例值时直接抛错（lib/auth.ts:30-52）。
  • 中间件重定向：已登录访问登录页由服务端跳转，避免客户端跳转与 token 判断不一致造成重定向循环（middleware.ts:19-27）。
P1-10改密后无法登出其它设备

会话采用 JWT 策略且没有「token 版本号」机制，改密码只更新 password 字段。已签发的 token 在其它设备上继续有效，直到自然过期（默认 30 天）。用户改密的心理预期是"踢掉所有登录"，实际做不到。

lib/auth.ts:199 session: { strategy: "jwt" } ← 无 maxAge 覆盖，用默认 30 天 app/api/account/route.ts:76-91 updateData 仅含 username / password / mustChangePassword 缺失 User 模型无 sessionVersion / tokenVersion 字段 缺失 登录时未把版本号写进 token，session 回调也未校验

建议：User 增加 sessionVersion Int，登录写入 token、改密时自增，并在 jwt 回调比对版本；不一致即视为失效。同时补一个「登出全部设备」入口。

观察限流为进程内内存态

lib/server.ts:287 与 lib/auth.ts:64 的限流桶都存于进程内存：单容器部署有效，但重启即清零；若将来横向扩容，各副本独立计数会削弱限流强度。代码注释已声明该限制，属已知取舍。

内核机制 · 数据一致性

备份、恢复、重置三件套存在范围不对称与破坏性操作缺少二次验证两类问题，构成本轮新增的两个 P0。

P0-4 数据丢失备份只覆盖 4 张表，恢复即丢失作品集 / 技能云 / 公告

备份结构固定为 profile + socialLinks + siteLinks + friendLinks，恢复时也只清空这三张链接表。但后台「数据管理」面板的宣传语是"备份与恢复站点数据"。用户导出备份 → 重置或换机 → 恢复，作品集、技能云、公告、媒体库记录会全部消失，界面上没有任何提示。

lib/backup.ts:8-15 BackupData = { profile, socialLinks, siteLinks, friendLinks } ← 仅 4 项 app/api/backup/route.ts:16-21 findMany 仅查这 4 张表 lib/backup.ts:100-102 restore 仅 deleteMany socialLink / siteLink / friendLink 未纳入备份的表（9 张） Project（作品集）· Skill（技能云）· SiteAnnouncement（公告）· ImageAsset（媒体库索引） SiteLinkClick（点击统计）· VisitStat · VisitRecord · User（账号）· UpdateRecord

建议：把 Project / Skill / SiteAnnouncement 纳入备份与恢复（各自补 zod 校验）；统计类表可显式排除，但必须在 DataPanel 中写明"备份范围"清单，避免用户误判为完整备份。

P0-5 安全「恢复默认状态」可一键把管理员密码降级为 123456

重置流程会把 admin 账号密码改回 123456 并置 mustChangePassword，而这一步只要求前端勾选一个确认框，不校验当前密码、不要求任何二次验证。会话一旦被窃取，攻击者可远程把账号降级到已知弱口令，完成持久化控制。

app/api/reset-default/route.ts:128-133 const hashed = await bcrypt.hash("123456", 10); await updateFn?.({ where: { id: adminUser.id }, data: { password: hashed, mustChangePassword: true } }); 鉴权强度对比 app/api/reset-default/route.ts:48-60 仅 requireSession() + URL 参数 confirm=true app/api/account/route.ts:62-66 修改密码要求 bcrypt.compare(currentPassword, …) ✓

建议：重置请求体必须附带当前密码并做 bcrypt 校验；或重置后强制跳转登录页并作废全部会话。

P1-13保存链接会让点击统计永久分裂

链接的批量保存策略是清空后重新插入，因此每次保存后所有链接的自增 id 都会变。而点击统计按 linkId 做 upsert、热门链接榜直接读该表且不做关联。结果是：保存一次链接后，后续点击写入新 id 行，旧行成为孤儿，同一个链接会在排行榜上出现多行，历史计数被永久拆散。

lib/server.ts:443-450 $transaction: deleteMany() → createMany(items) ← createMany 不写 id，全部生成新自增 id lib/validation.ts:518-540 siteLinkSchema 不含 id 字段（zod 会剥离未知键） app/api/stats/click/route.ts:35-39 upsert({ where: { linkId } }) ← 按 id 聚合 app/api/stats/dashboard/route.ts:104-107 siteLinkClick.findMany({ orderBy: { count: "desc" }, take: 8 }) ← 无 join siteLink，孤儿行照样上榜

建议：链接批量保存改为按 id 增量 upsert（项目与技能已有 syncByUpsert 可复用），保持 id 稳定；或改按 url 作为点击聚合键。

P1-11备份格式没有向前兼容能力

parseBackup 对版本号做严格等值判断，不等即拒绝；而注释声称"升级格式时递增，恢复端按版本分流"，实际代码里没有任何分流逻辑。一旦将来把 BACKUP_VERSION 提升到 2，用户此前保存的所有 v1 备份文件将全部无法恢复。

lib/backup.ts:4 /** 备份文件版本（升级格式时递增，恢复端按版本分流） */ lib/backup.ts:38 if (obj.version !== BACKUP_VERSION) return { ok: false, error: "不支持的备份版本…" }; ← 只有等值判断，无版本分支 app/api/backup/route.ts:30 文件名仅到日期（YYYYMMDD），同日多次备份靠浏览器加序号区分
P1-12重置默认只清数据库，不删磁盘文件

重置会清空 ImageAsset 表，但不删除 uploads 目录里的实际图片文件。这些文件从此既无记录可查、也不会被任何清理流程回收，成为永久孤儿文件，持续占用磁盘且无法从界面察觉。

app/api/reset-default/route.ts:35 { dbTable: "ImageAsset", modelKey: "imageAsset" } ← 仅删记录 app/api/reset-default/route.ts:70-87 循环内只做 deleteMany，无任何文件系统操作 对照 app/api/media/[id]/route.ts 单张删除时会同步删除物理文件 ✓
观察整表同步语义与性能
  • 会删除未提交行：lib/upsert.ts:54-58 把"库中存在但本次未提交"的行直接删除。多人同时编辑时，后保存者会静默删掉前者新增的记录（个人站点风险可控，但需知晓）。
  • 逐行 await：lib/upsert.ts:44-52 对每个条目串行 update/create，条数多时是 N 次数据库往返。作品 / 技能 / 链接通常数十条，可接受，但没有批量优化空间。

内核机制 · 更新通道与统计采集

更新通道的工程细节相当成熟（握手文件 + 宿主机定时执行器 + 原子认领 + 权限自愈 + 数据库快照）。问题集中在失败路径的一致性，以及统计侧缺少数据卫生处理。

设计良好更新通道的工程细节
  • 无命令注入：version 全程加引号传递（update-watch.sh:265,289,295），回滚目标受 rollbackTargets() 白名单约束（update/trigger/route.ts:86-89）。
  • 原子认领防并发：mv 重命名认领请求（update-watch.sh:230），配合 trap … EXIT 清理认领文件（:236），避免残留文件永久阻塞后续更新。
  • 权限自愈：每次调度校正 data/deploy 属主，根治容器非 root 写 request.json 报 EACCES 的问题（:74-82）。
  • 数据库快照：更新 / 回滚前各备份一次，仅保留最近 20 份；回滚时按目标版本还原并清理 WAL/SHM 残留（:126-152）。
  • 优雅停机：先 docker compose stop 让 SQLite WAL 落盘，再执行备份 / 还原（:273-283）。
P1-14更新中途失败会留下「代码已切、容器未更」的混合状态

git checkout 成功后，后续任一环节（构建、拉镜像、启动）失败时只写回 failed 结果并退出，不会回滚已切换的代码。此时仓库处于新版本、运行中的容器仍是旧版本，versions.json 未更新、数据库快照也未还原 —— 用户只看到"更新失败"，却不知系统实际处于混合状态。

scripts/update-watch.sh:265-271 git checkout "$version" ← 代码已切换 scripts/update-watch.sh:287-300 构建 / pull / up 任一失败 → write_result failed; exit 0 ← 无 git checkout "$cur" 回退 scripts/update-watch.sh:303-307 仅在成功路径写 versions.json

建议：失败时自动 git checkout "$cur" 回退代码并重新拉起容器；至少应在结果文案中明确写出"代码已切至 X，容器仍运行 Y"。

次要更新通道的细节瑕疵
  • 校验逻辑双实现：scripts/update.sh:14-18 的命令行入口对 rollback 不校验目标是否在回滚白名单内，与 API 侧 update/trigger/route.ts:86-89 的严格校验行为不一致。
  • JSON 解析方式脆弱：update-watch.sh:63-65 用 sed 正则提取字段，依赖"键值独占一行"的书写格式；description 含引号或换行时会截断。
  • 分离 HEAD：git checkout "$version" 使仓库进入 detached HEAD，后续手动 git pull 需先切回分支。
  • 更新模式无标签格式白名单：tag 直接取自 GitHub release 的 tag_name，虽不构成注入（已加引号），但会原样写入数据库、versions.json 与操作日志。
P1-15访问统计没有爬虫过滤，PV 天然虚高

采集端只从 UA 解析设备 / 系统 / 浏览器，没有任何爬虫或机器人识别。搜索引擎蜘蛛、监控探活、各类扫描器都会被计入 PV 与 UV，并被归类进"设备分布"与"地域分布"，导致仪表盘数字与实际访客量存在系统性偏差；站长自己的访问同样计入。

app/api/stats/route.ts:74-81 parseUserAgent(ua) → { device, os, browser } lib/ua.ts:17-69 仅判定 desktop / mobile / tablet，无 bot 分支 缺失 无 isBot / 已知爬虫 UA 名单 缺失 无"排除站长自身"机制（Cookie 标记或 IP 白名单）

建议：采集中加入常见爬虫 UA 识别并在入库前丢弃；对已登录管理员的访问打标排除或单独归类。

P1-16统计数据没有保留策略，单调增长

VisitRecord 每个访问产生一行，VisitStat 每天一行。前者虽有 (date, hour) 索引，但没有任何归档或清理机制：操作日志有手动清理入口，访问明细却完全没有。长期运行后单表会持续膨胀，而地域聚合需要对窗口内全部去重 IP 做解析，成本随时间上升。

prisma/schema.prisma:201-215 VisitRecord（每访问一行，含 ip / ua / referrer） app/api/stats/dashboard/route.ts:122-125 对窗口内全部去重 IP 解析地域（无上限保护） 对照 components/admin/OperationLogPanel.tsx 已有「按时间段清理」入口 ✓ 缺失 访问明细的清理 / 归档入口

审计方式：全仓库静态分析（只读），逐字段 grep 验证生效链路，交叉核对 schema → validation → API → hooks → 组件 的完整数据流；第二轮追加认证、备份/恢复/重置、更新通道、统计采集与无障碍审计。
本报告未修改任何项目文件。
